## 2. 文档定位

本文档面向后端工程落地，目标是把 [后端设计文档.md](/C:/dev/copypaste/agent-workshop/docs/后端设计文档.md) 转化为可直接开工的开发基线。

| 文档 | 作用 |
|---|---|
| 后端设计文档 | 定义系统目标、技术边界、架构原则 |
| 后端开发文档 | 定义代码结构、模块职责、接口、流程、测试、部署与验收方式 |

本文档解决以下开发问题：

| 问题 | 输出内容 |
|---|---|
| 代码仓库如何组织 | 单仓结构、应用边界、共享包边界 |
| 服务如何拆分 | API、Worker、Bridge、凭证、文件、MCP 的具体职责 |
| run 如何启动 | 从前端创建 run 到容器销毁的完整执行链路 |
| Codex CLI 跑在哪 | 固定在 runner image 容器内，由 Bridge 以 PTY 拉起 |
| session 如何存 | 当前为 PostgreSQL/文件双轨元数据 + `objectStore` session archive 字节链，并保留 legacy 本地归档兼容读取；目标态为 PostgreSQL 权威元数据 + 对象存储 session pack |
| 文件如何传 | 预签名上传 + 对象存储 + target path 实时浏览 |
| 第三方 MCP 和私有凭证如何处理 | MCP Registry + Binding + Credential Broker |

## 3. 开发基线

### 3.1 总体目标

| 目标 | 开发要求 |
|---|---|
| 统一后端主栈 | API、Worker、Bridge、共享契约全部使用 TypeScript |
| 每个 run 强隔离 | 每个 run 必须是独立容器、独立 HOME、独立 CODEX_HOME、独立 secrets |
| Codex 可实时对话 | 前端能通过 WebSocket 与 run 对话，并实时接收结构化事件 |
| target path 可视化 | 用户能浏览当前 run 的目标目录、预览文件、下载文件 |
| session 可复用 | session 以平台 pack 形式持久化、版本化、可 fork |
| MCP 可治理 | 支持第一方、企业托管、第三方不受控 MCP 的统一注册与注入 |
| 凭证可治理 | 明文凭证不进入数据库，不直接暴露给 API 业务层 |

| 约束 | 说明 |

## 7. 核心链路实现

### 7.1 创建 run 链路

| 步骤 | 组件 | 动作 |
|---|---|---|
| 1 | API | 校验用户、workspace、task_version、session_version、MCP binding、凭证要求 |
| 2 | API | 写入 `runs`、`run_inputs` 初始记录 |
| 3 | API | 将 run 入队 `run.start`，并在终态时调度 `run.cleanup` 延迟清理 |
| 4 | Worker | 拉取 session pack、准备宿主机工作目录、拉取凭证 |
| 5 | Worker | 启动 run 容器与 Bridge |
| 6 | Bridge | 注册到 API，准备 PTY、文件监听、MCP 配置 |
| 7 | Worker | 将 run 状态推进为 `RUNNING` |
| 8 | API | 向前端推送 `run.status` 和初始系统引导消息 |

### 7.1.1 服务启动模板解析链

| 步骤 | 组件 | 动作 |
|---|---|---|
| 1 | Catalog API | 校验 `serviceId`、`workspaceContextKey` 与入口面 `entrySurface` 的可见性 |
| 2 | Catalog Repository | 读取显式 launch template 记录；优先按当前入口面，其次回退到 `dashboard` 模板 |
| 3 | Creator Service | 若当前 `serviceId + workspaceContextKey` 存在 `active` activation，则从 package `versionLine` 解析 `taskVersionId / sessionVersionId` |
| 4 | Catalog Service | 当目录模板行缺失但 Creator activation 存在时，按 `context.root + runs/<serviceId>` 派生 `targetRoot`，并沿用服务级 binding |
| 5 | Catalog API | 返回 `launchTemplate`，包含 `createRunInput` 与 `resolution.source = creator-activation | catalog-default` |

### 7.2 用户消息进入 Codex 链路

| 步骤 | 组件 | 动作 |
|---|---|---|
| 1 | 前端 | 通过 `WS /ws/runs/:id` 发送 `user.message` |
| 2 | API | 校验 run 访问权和状态 |
| 3 | API | 根据 `runId -> bridge connection` 转发消息 |
| 4 | Bridge | 调用 `sendMessage()` 写入 Codex PTY |
| 5 | Codex CLI | 输出文本、工具调用、文件变化 |
| 6 | Bridge | 解析 stdout/stderr 为结构化事件 |
| 7 | API | 向所有订阅该 run 的客户端推送事件 |

### 7.3 文件链路

| 场景 | 路径 |
|---|---|
| 输入文件上传 | 前端 -> API 获取预签名 -> 直传对象存储 -> API 记录元数据 -> Worker 挂载到 `/workspace/inputs` |
| 输出文件收集 | 容器内文件变化 -> Bridge 发现 -> 上传对象存储 -> API 记 `run_artifacts` -> 前端收到 `artifact.ready` |
| target path 浏览 | 前端请求 API -> API 读取 target path 树/文件；目录存在时可实时扫描，目录被回收时自动回退到 `run_files` 索引读模型 |

### 10.1 队列设计

### 10.1.1 当前已落地的运行编排基线

| 能力 | 当前实现 |
|---|---|
| 编排入口 | `app/api` 内的 `EmbeddedRunOrchestrator` 会在创建 run 后立即入队 |
| 分发模式 | 通过 `LINGBAN_RUNTIME_DISPATCH_MODE` 选择 `embedded / bullmq` |
| 并发控制 | 通过 `LINGBAN_RUNTIME_MAX_CONCURRENT_RUNS` 控制嵌入式编排与 BullMQ worker 的并发 run 数，当前默认值为 `2` |
| 启动恢复 | API 启动时会自动重排 `CREATED/READY/QUEUED/STARTING` run；独立 BullMQ worker 启动时会拉取 recovery candidates，并执行 `enqueue-start`、`mark-orphan-failed` 与 `schedule-cleanup` |
| 孤儿会话处理 | `RUNNING/WAITING_APPROVAL` 在 API 重启后会进入 `LINGBAN_RUNTIME_ORPHAN_GRACE_MS` grace window；bridge 若未及时重新 register，则会被标记为 `FAILED` |
| 终态清理 | 终态 run 会按 `LINGBAN_TERMINAL_WORKSPACE_TTL_MS` 延迟投递 `run.cleanup` 作业，避免 cleanup 只依赖进程内定时器；worker 重启后会基于 `runtime.finishedAt/run.updatedAt` 计算剩余 TTL 并补投 cleanup |
| 独立 worker 基线 | `app/run-worker/src/daemon.ts` 已具备 BullMQ `run.start` 队列消费、runtime 拉起、completion 监控，以及 `run.cleanup` 队列消费回收 workspace |
| worker 运维面 | `app/run-worker/src/ops-http.ts` 已补齐 `/health`、`/readyz`、`/diagnostics`、`/metrics`，可查看 runtime backend readiness、queue component readiness、active runs、recovery summary、DLQ 计数与全局 QueueEvents 计数 |
| API 平台诊断聚合 | `app/api/src/app/runtime-diagnostics.ts` 已能聚合本地 bridge registry / orchestrator / recovery 诊断，以及远端 worker ops 和已注册 bridge control endpoint 的运行诊断；`/readyz` 会在显式配置 `LINGBAN_WORKER_OPS_BASE_URL` 后把 worker ops 纳入依赖判断，`/internal/metrics` 会导出平台级 probe 指标 |
| control 面恢复 | bridge register 已携带外部可达 `controlUrl`，并支持周期性 refresh，API 重启后可重新附着 controller |
| 进程退出行为 | 嵌入式模式的 cleanup timer 已 `unref`；BullMQ 模式的终态回收改由延迟队列作业承接 |
| 当前缺口 | Redis 正式部署、自动补偿与跨节点治理联动，以及 Docker daemon 实机联调与长时间运行证据仍未完成 |

### 10.2.1 当前 credential broker 基线

| 项 | 当前实现 |
|---|---|
| provider | `local-envelope`、`vault-transit-http`、`aws-kms-envelope` |
| 加密方式 | `local-envelope` 使用 `AES-256-GCM` envelope；`vault-transit-http` 通过 Vault Transit `encrypt/decrypt` API 托管密文；`aws-kms-envelope` 通过 KMS `GenerateDataKey/Decrypt/DescribeKey` 生成 data key，再以本地 `AES-256-GCM` 完成 envelope seal/open |
| 持久化载体 | discriminated `secretEnvelope` 持久化到 file/postgres-backed credentials repository，并记录 `brokerKind` 与 `keyId` |
| 轮换语义 | `rotateCredential()` 会递增 `secretVersion`，按当前 active broker 重新 seal secret，并保留可审计的 `activeKeyId` / `brokerKind` |
| 运行时下发 | worker/bridge 在启动前调用 `/internal/runs/:id/credentials/materialize` 获取短租约 secret map |
| 审计/证据 | `credential-materializations-state.json` / `credential-audit-events-state.json` 或 `lingban_credential_materializations` / `lingban_credential_audit_events` 记录物化租约、物化阻断和生命周期事件；`tests/credential-broker-vault.smoke.test.mjs` 与 `tests/credential-broker-aws-kms.smoke.test.mjs` 覆盖 seal/rotate/materialize/health |
| 生命周期治理 | 后台 `credentialLifecycleManager` 周期 sweep；`credentialLifecycleCallbackManager` 负责 suspend/revoke 后的 provider callback delivery ledger、立即投递、失败重试、结构化审计与 `/internal/credentials/callbacks`、`/internal/credentials/callbacks/sweep` 诊断入口；当前已支持 static headers、bearer、`hmac-sha256`、`oauth-client-credentials`、`private_key_jwt` 与 callback/token endpoint `mTLS` 传输，以及 `eventType` / `eventVersion` / attempt metadata payload 策略 |
| 当前缺口 | AWS KMS adapter 已落地；GCP/Azure KMS 与 HSM adapter、更多 provider callback adapter、provider-specific canonical signing profile 与更细粒度 stdio 执行隔离仍未闭环；usage graph、active-run impact action、自动到期冻结、structured secret audit、callback retry/audit、动态 OAuth/JWT callback auth 与 mTLS callback transport 已落地 |

### 10.4 Worker 并发与重试

| 项目 | 策略 |
|---|---|
| 单 worker 并发数 | 当前嵌入式编排与独立 BullMQ worker 均使用 `LINGBAN_RUNTIME_MAX_CONCURRENT_RUNS` 控制；后续继续以 Docker 主机 CPU/内存为约束做容量配置 |
| `run.start` 重试 | 默认有限重试，仅对可恢复错误重试 |
| `run.cleanup` 执行 | 当前以延迟队列作业消费 worker 管理目录清理，支持 API/worker 重启后的持久化恢复；worker 启动恢复会按剩余 TTL 补投 cleanup |
| 不可恢复错误 | 直接标记 `FAILED`，记录标准错误码 |
| 孤儿 run 处理 | 当前 API 重启时会进入 orphan grace；bridge 若完成 refresh register，则保持 run 存活 |
| 终态目录清理 | 当前通过 `LINGBAN_TERMINAL_WORKSPACE_TTL_MS` 配合 `run.cleanup` 延迟作业清理 worker 管理目录；恢复阶段优先使用 `runtime.finishedAt` 计算剩余延迟，缺失时回退到 `run.updatedAt` |
| 僵尸容器清理 | 定时扫描 `run.status != final` 且容器不存在的异常 run |

### 10.5 失败分类

| 类型 | 处理方式 |
|---|---|
| 容器启动失败 | 标记 `FAILED`，记录 `container_start_failed` |
| Bridge 注册超时 | 强制销毁容器并标记失败 |
| session pack 解包失败 | 终止 run，进入失败态 |
| 凭证物化失败 | 终止 run，进入失败态 |
| artifact 上传失败 | run 可结束，但需补偿重传任务 |

### 11.5 Bridge 恢复语义

| 项目 | 当前实现 |
|---|---|
| 自动恢复触发 | Codex CLI 非零退出且 bridge 未收到显式 stop/cancel 时进入恢复流程 |
| 尝试预算 | `LINGBAN_BRIDGE_CODEX_RESTART_MAX_ATTEMPTS` 控制最大自动恢复次数，支持 `0` 关闭自动恢复 |
| 恢复退避 | `LINGBAN_BRIDGE_CODEX_RESTART_BACKOFF_MS` 控制下一次拉起前的退避时间，支持 `0` |
| 预算重置窗口 | `LINGBAN_BRIDGE_CODEX_RESTART_RESET_WINDOW_MS` 控制稳定运行后的恢复预算重置窗口，支持 `0` 关闭窗口 |
| 输入回放 | `CodexSession` 缓存用户消息与审批输入，恢复成功后重新写入 PTY |
| 恢复期控制面 | `/diagnostics` 暴露 `recovering`、`restartBudgetUsed`、`restartAttemptsTotal`、`restartSuccessTotal`、`restartFailuresTotal`、`replayHistoryCount` 等字段 |

| 当前边界 | 仅覆盖 bridge 进程存活期间的会话自愈；bridge 进程重启后的持久化恢复尚未落地 |

| 审批 | 高风险第三方 MCP 可挂审批策略 |

### 25.4 签名规则

1. Packer 先构建不含 `signature` 的 canonical manifest。
2. Canonical JSON 递归排序 Object Key，Array 顺序保持原样。
3. HMAC-SHA256 输出 Hex，Ed25519 输出 Base64。
4. Packer 将签名写回 `manifest.json` 后重新打包。
5. `session_versions.signature_*` 必须和内嵌签名完全一致。
6. Run 恢复前验证对象大小、对象哈希、Key ID、算法和签名值。

### 25.5 Raw Capture 访问规范

Raw Capture 对象不进入普通文件浏览接口。访问流程：

```text
owner/admin/creator 登录
→ 提交至少 8 字符访问原因
→ 校验工作区与 Capture
→ 写入 access audit
→ S3 返回短期签名 URL
  或 Filesystem Object Store 返回 API 代理流
```

Audit 字段包括 `auditId`、`captureId`、`workspaceId`、`objectType`、`objectSha256`、`actorUserId`、`reason`、`accessMode`、`requestedAt` 和 `expiresAt`。

### 25.6 Legacy 迁移开发规则

1. Legacy Archive 读取过程不修改旧表和旧对象。
2. Dry Run 完成反序列化、v2 构建、签名和最终 Hash 计算，不写对象。
3. Apply 写入签名 Pack、迁移报告、Session 和 Detached Version。
4. `sourceType=legacy-imported`、`legacyIncomplete=true`、本地 Revision/Replay FK 为 null。
5. 旧 Parent Version 只在目标库已存在时建立 FK。
6. Active Binding 拒绝 `legacyIncomplete=true` 的版本。
7. `POST /v1/session-versions/import` 先调用 v2 Reader；仅在格式不匹配时调用 v1 Reader 和迁移器。

## 26. Provider 默认路由与平台凭证实现约束

### 26.1 路由层级

| 层级 | Binding Scope | Credential 归属 | 生效范围 | 优先级 |
|---|---|---|---|---:|
| 平台默认 | `platform` | Admin 管理工作区中的托管 Credential | 所有工作区 | 1 |
| 工作区覆盖 | `workspace` | 当前工作区 Credential | 当前工作区 | 2 |
| Run 显式选择 | 引用有效 Binding | 继承 Binding | 当前 Run | 3 |

Provider Resolver 先筛除已停用 Provider 和 Binding，再按工作区默认、平台默认、工作区优先级、平台优先级依次解析。显式 Provider 选择优先匹配工作区绑定，再匹配平台绑定。模型覆盖必须通过 `allowUserOverride` 和 Provider 模型白名单校验。

### 26.2 平台 Credential 最小授权

1. `ResolvedRunProvider.bindingScope` 固定记录 `platform` 或 `workspace`。
2. API 构建 Start Run Payload 时只把已解析 Provider Credential 加入运行凭证集合。
3. 跨工作区 Credential 仅在 `bindingScope=platform` 且 Credential ID 位于当前 Run 的 `platformCredentialIds` 时允许解析和物化。
4. Internal Credential Materialize 路由从服务端 Start Run Payload 生成白名单，禁止 Worker 或前端自行扩大范围。
5. Materialization Lease 记录目标 Run Workspace；Credential Audit 继续记录 Credential 管理 Workspace、Secret Version 和 Broker Kind。
6. 前端和公共 API 永不返回 API Key 明文；平台继承绑定在 Dashboard 中显示“平台托管凭证”。

### 26.3 启动失败策略

Creator Source Run 在 Provider 解析结果为空时返回 `409 PROVIDER_BINDING_UNAVAILABLE`。Dashboard 在 Provider Binding 查询完成且结果为空时禁用“启动空白 Codex”，并提供 `/workspace/settings/providers` 修复入口。该校验必须发生在容器启动和首条消息发送之前。

### 26.4 Codex CLI Provider 配置生成

Worker 的 `materializeRunRuntime()` 在启动容器前生成 `${CODEX_HOME}/config.toml`，文件权限固定为 `0600`。配置结构如下：

```toml
model = "<resolved-model>"
model_provider = "lingban_runtime"

[model_providers.lingban_runtime]
name = "<provider-display-name>"
base_url = "<resolved-provider-base-url>"
env_key = "<provider-auth-env-name>"
wire_api = "responses"
requires_openai_auth = false
supports_websockets = false

[projects."/workspace/target"]
trust_level = "trusted"
```

| 字段 | 来源 | 约束 |
|---|---|---|
| `model` | `StartRunJobPayload.provider.model` | 必须通过 Provider 模型白名单解析 |
| `model_provider` | Worker 固定值 `lingban_runtime` | 每个 Run 使用独立配置目录 |
| `base_url` | `StartRunJobPayload.provider.baseUrl` | 必须经过 Provider URL 校验与出网策略物化 |
| `env_key` | `StartRunJobPayload.provider.authEnvName` | 只保存变量名，禁止保存 API Key |
| `wire_api` | Worker 固定值 `responses` | Provider 必须兼容 OpenAI Responses API |
| `requires_openai_auth` | Worker 固定值 `false` | 采用平台 Credential Broker 注入的第三方鉴权 |
| `supports_websockets` | Worker 固定值 `false` | 第三方兼容端点默认使用 HTTP 流式协议 |
| `projects` | 宿主机和容器 Target Path | 两条路径均声明 `trusted` |

`runtime-config.json`、Run 事件、日志和 Session Pack 禁止保存 API Key。Bridge 启动后从容器环境读取 `env_key` 对应值。运行验收需要同时检查配置文件无密钥、Provider 请求目标正确、Codex 响应成功和 Target Path 文件落盘。

### 26.5 发布启动门禁

`install-release.sh` 先重启 API 并等待 `${API_PORT}/readyz`，随后重启 Worker 并等待 `${LINGBAN_WORKER_OPS_PORT}/readyz`。任一 Readiness 失败即终止安装并输出服务日志，防止 Worker 恢复扫描在 API 初始化阶段产生一次性失败。

### 26.6 Agent 公网访问门禁

新建 Run 默认启用 Codex workspace-write 出站网络，并在每次 `turn/start` 显式传入 `sandboxPolicy.networkAccess=true`。生产环境默认关闭 Runtime egress proxy 与 egress firewall，保证 npm、pip、Git、Playwright、网页和第三方 API 可访问。

Docker 与 Local Process 均必须使用 Run 独立的 `HOME/CODEX_HOME/TMPDIR`。完整配置、协议字段、Runner 工具集与 HZ01 端到端证据见 `docs/20260718Agent联网修复说明.md`。
