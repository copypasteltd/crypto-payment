# 灵办词元 系统可用性分析

## 1. 结论摘要

| 维度 | 当前判断 | 风险等级 | 结论 |
|---|---|---:|---|
| 产品入口可用性 | 小程序/H5 面向轻度用户，Web 面向重度用户和 Creator，分层合理 | 低 | 产品形态具备落地基础 |
| 任务启动可用性 | 动态表单、授权、确认、云端运行链路明确 | 中 | 需要强化表单校验、授权失败恢复、草稿机制 |
| Session Fork 可用性 | 核心差异成立，但受 session 状态、外部系统漂移、runtime 兼容影响 | 高 | 首发阶段必须限制场景和 runtime |
| 云端运行可用性 | 需要容器隔离、队列调度、超时控制、重试和审计 | 高 | 属于系统稳定性的核心工程投入 |
| 移动端交互可用性 | 阶段进度、确认弹窗、结果页适合轻度用户 | 中 | 需要异步通知和失败可解释能力 |
| Creator 生产可用性 | Session Builder、Slot 配置、Trace Viewer 方向正确 | 中 | 首发阶段应控制 Creator 工具复杂度 |
| 企业治理可用性 | 权限、密钥、审计、成本控制方向完整 | 中 | 初期建议只支持基础租户隔离和密钥托管 |
| 安全合规可用性 | 有关键动作确认和 Execution Ledger 设计 | 高 | 高风险场景需延后，优先低合规风险场景 |
| 运维可用性 | 指标体系已有雏形 | 中 | 需要补齐 SLO、告警、降级、任务补偿 |

总体判断：**灵办词元具备完整系统方向下的首发阶段可用性基础，生产级可用性取决于 Session Fork Runtime、Cloud Runner、Credential Vault、Execution Ledger、State Validator 五个模块的工程质量。**

第一阶段应选择低合规风险、输入输出明确、外部状态漂移较低的业务流程，例如 Seedance API 短剧生成、素材批量处理、视频脚本与分镜生成。报税、支付、政务提交、金融操作不适合作为首批核心场景。

## 2. 可用性分析范围

本文中的系统可用性覆盖以下八类：

| 类别 | 说明 |
|---|---|
| 产品可用性 | 用户是否能低成本理解、启动、完成任务 |
| 功能可用性 | 核心功能是否形成完整闭环 |
| 运行可用性 | 云端 agent 是否能稳定执行任务 |
| 复用可用性 | session fork 是否能在新用户输入下持续有效 |
| 数据可用性 | 输入、输出、trace、ledger 是否可靠存取 |
| 安全可用性 | 授权、密钥、隔离、确认、审计是否可控 |
| 运维可用性 | 监控、告警、重试、恢复、降级是否完备 |
| 商业可用性 | 成本、成功率、复用率是否支撑商业模型 |

## 3. 系统链路可用性

### 3.1 主链路

```text
任务选择
-> 任务详情
-> Slot 表单填写
-> 文件/API/账号授权
-> 成本与风险确认
-> 创建 forked session
-> 云端 agent 执行
-> 关键动作确认
-> 结果生成
-> Execution Ledger 归档
-> 通知与结果交付
```

### 3.2 链路风险点

| 链路节点 | 可用性风险 | 影响 | 建议措施 |
|---|---|---|---|
| 任务选择 | 任务描述不清晰 | 用户误用、启动率低 | 任务卡片展示输入、输出、耗时、费用、授权要求 |
| Slot 表单 | 字段过多或校验不足 | 表单流失、运行失败 | 分步填写、字段默认值、格式校验、草稿保存 |
| 文件上传 | 大文件失败、格式不支持 | 任务无法启动 | 分片上传、格式白名单、大小限制、失败重传 |
| API 授权 | key 无效、额度不足、权限不足 | 执行中断 | 启动前校验、额度探测、授权状态缓存 |
| 创建 fork | session 版本不可用 | 任务无法运行 | 发布前健康检查、版本冻结、回滚能力 |
| 云端执行 | agent 卡住、工具失败、第三方超时 | 完成率下降 | 队列、超时、重试、任务心跳、人工接管 |
| 关键确认 | 用户未及时响应 | 任务长时间挂起 | 小程序/短信/企业微信通知、确认超时策略 |
| 结果交付 | 输出文件过期或丢失 | 用户无法获得结果 | 对象存储、下载审计、结果保留策略 |
| Ledger 归档 | 记录不完整 | 无法审计和复盘 | 事件流写入、幂等 ID、失败补写 |

## 4. 产品可用性

### 4.1 端侧分层

| 端侧 | 目标用户 | 可用性优势 | 可用性风险 | 建议 |
|---|---|---|---|---|
| 小程序/H5 | 轻度用户、临时用户、一线业务人员 | 低门槛、触达快、适合异步确认 | 承载复杂配置能力弱 | 只保留选择、填写、授权、进度、确认、结果 |
| Web Dashboard | 重度用户、Creator、管理员 | 信息密度高、适合调试和治理 | 学习成本高 | 按 Run、Creator、Trace、Admin 分区 |
| 云端 Runtime | 所有用户 | 用户无需安装环境 | 成本和稳定性压力集中 | 容器化、队列化、按任务隔离 |

### 4.2 移动端可用性评价

| 指标 | 目标建议 | 说明 |
|---|---:|---|
| 首次任务启动步骤 | <= 5 步 | 任务详情、填写、授权、确认、启动 |
| 首屏理解时间 | <= 10 秒 | 用户需快速判断任务能完成什么 |
| 表单完成率 | >= 70% | 首发阶段重点优化指标 |
| 授权完成率 | >= 60% | API key 和 OAuth 是主要流失点 |
| 待确认响应时长 | P50 <= 5 分钟 | 依赖通知机制 |
| 结果查看率 | >= 80% | 结果页要直接呈现核心输出 |

### 4.3 Web 可用性评价

| 工作区 | 关键可用性要求 | 首发标准 |
|---|---|---|
| Run Workspace | 批量运行、状态筛选、失败重试 | 支持 CSV 上传、字段映射、批量状态 |
| Creator Studio | 录制、脱敏、slot 配置、测试 fork | 支持单 session 发布闭环 |
| Trace & Debug | 事件时间线、错误节点、工具摘要 | 支持基础事件过滤 |
| Admin Console | 成员、密钥、成本、审计 | 支持基础组织权限和 API key 托管 |

## 5. Session Fork Runtime 可用性

### 5.1 核心可用性判断

Session Fork Runtime 是系统差异化核心，也是最大工程风险。其可用性取决于以下条件：

| 条件 | 必要性 | 当前方案覆盖 | 风险 |
|---|---:|---:|---:|
| session trace 可完整记录 | 高 | 已覆盖 | 中 |
| 敏感字段可准确替换 | 高 | 已覆盖 | 高 |
| slot schema 可稳定绑定 | 高 | 已覆盖 | 中 |
| runtime snapshot 可恢复 | 高 | 部分覆盖 | 高 |
| agent runner 可持续执行 | 高 | 部分覆盖 | 高 |
| 外部系统状态可校验 | 高 | 已提出 State Validator | 高 |
| 失败可重试或接管 | 高 | 部分覆盖 | 中 |
| ledger 可完整审计 | 高 | 已覆盖 | 中 |

### 5.2 Session Fork 失败类型

| 失败类型 | 示例 | 检测方式 | 恢复策略 |
|---|---|---|---|
| Slot 缺失 | 用户未填 API key、素材缺失 | 表单校验 | 阻止启动并提示补全 |
| Slot 语义错误 | 时长格式错误、预算过低 | schema + 业务校验 | 返回修改 |
| 授权失败 | API key 无效、OAuth 过期 | 启动前探测 | 重新授权 |
| Runtime 不兼容 | CLI 版本变化、依赖缺失 | runtime health check | 使用冻结镜像 |
| Trace 漂移 | 页面结构变化、API schema 变化 | State Validator | 进入恢复分支或人工接管 |
| Agent 卡住 | 循环重试、长时间无工具调用 | 心跳检测 | 超时终止、重启、接管 |
| 输出不合格 | 视频失败、文件缺失 | 结果校验器 | 自动重试或返回失败原因 |
| Ledger 缺失 | 工具调用未记录 | 事件写入监控 | 补偿写入、标记异常 |

### 5.3 可用性门槛

| 阶段 | Fork 成功率目标 | 任务完成率目标 | 说明 |
|---|---:|---:|---|
| 技术验证 | >= 50% | >= 40% | 验证 session fork 基本可行 |
| 首发内测 | >= 70% | >= 65% | 限定任务、限定 runtime、限定输入 |
| 公测 | >= 85% | >= 80% | 支持失败恢复和可解释错误 |
| 企业生产 | >= 95% | >= 90% | 需要 SLA、审计、隔离、回滚 |

## 6. 云端运行可用性

### 6.1 Cloud Runner 关键能力

| 能力 | 必要性 | 缺失影响 |
|---|---:|---|
| 任务队列 | 高 | 高并发时任务丢失或阻塞 |
| 容器隔离 | 高 | 数据串扰和安全风险 |
| 超时控制 | 高 | agent 卡死导致资源耗尽 |
| 幂等任务 ID | 高 | 重试导致重复提交或重复扣费 |
| 资源配额 | 高 | 单任务消耗不可控 |
| 工具白名单 | 高 | agent 越权访问工具 |
| 网络策略 | 中 | 无法限制第三方访问范围 |
| 任务心跳 | 高 | 无法识别卡死任务 |
| 运行日志 | 高 | 无法定位失败原因 |
| 结果校验 | 高 | 用户拿到不完整结果 |

### 6.2 建议运行状态机

| 状态 | 含义 | 可迁移状态 |
|---|---|---|
| `DRAFT` | 用户填写中 | `READY`、`CANCELLED` |
| `READY` | 输入和授权已校验 | `QUEUED`、`CANCELLED` |
| `QUEUED` | 等待运行资源 | `RUNNING`、`FAILED` |
| `RUNNING` | agent 执行中 | `WAITING_APPROVAL`、`SUCCEEDED`、`FAILED`、`CANCELLED` |
| `WAITING_APPROVAL` | 等待用户确认 | `RUNNING`、`CANCELLED`、`EXPIRED` |
| `SUCCEEDED` | 执行成功 | `ARCHIVED` |
| `FAILED` | 执行失败 | `RETRYING`、`ARCHIVED` |
| `RETRYING` | 自动或人工重试 | `RUNNING`、`FAILED` |
| `CANCELLED` | 用户取消 | `ARCHIVED` |
| `EXPIRED` | 确认或资源超时 | `FAILED`、`ARCHIVED` |
| `ARCHIVED` | 归档完成 | 终态 |

## 7. 数据与审计可用性

### 7.1 数据对象

| 数据对象 | 可用性要求 | 存储建议 |
|---|---|---|
| User Input | 可追溯、可重放、可删除 | 关系型数据库 + 加密字段 |
| Uploaded Files | 可下载、可过期、可审计 | 对象存储 |
| Session Trace | 不可变、可索引、可过滤 | 事件流存储 + 搜索索引 |
| Runtime Snapshot | 可版本化、可回滚 | 镜像仓库 + 配置仓库 |
| Credential | 不明文暴露、可轮换、可吊销 | KMS / Vault |
| Execution Ledger | 完整、不可篡改、可导出 | 追加写日志 + 审计库 |
| Result Package | 可预览、可分享、可失效 | 对象存储 + 权限签名 |

| input_digest | 输入摘要 |
| credential_refs | 凭证引用 |
| tool_calls | 工具调用摘要 |
| approvals | 用户确认记录 |
| cost | 成本明细 |
| status | 最终状态 |
| failure_reason | 失败原因 |
| result_refs | 输出结果引用 |

### 8.1 风险等级

| 场景 | 风险等级 | 首发建议 |
|---|---:|---|
| 短剧生成 | 低 | 优先支持 |
| 素材处理 | 低 | 优先支持 |
| 脚本/分镜生成 | 低 | 优先支持 |
| 发票整理 | 中 | 支持前需做数据隔离和审计 |
| 网页资料采集 | 中 | 需要网络访问策略和合规提示 |
| 报税 | 高 | 后期专项设计 |
| 支付 | 高 | 后期专项设计 |
| 政务提交 | 高 | 后期专项设计 |
| 金融操作 | 高 | 后期专项设计 |

### 8.2 必要安全控制

| 控制项 | 优先级 | 说明 |
|---|---:|---|
| 密钥托管 | P0 | 用户 key 不进入 prompt，不写入 trace 明文 |
| 运行容器隔离 | P0 | 每个 run 独立容器和文件空间 |
| 工具权限白名单 | P0 | 按任务限制可用工具 |
| 高风险动作确认 | P0 | 提交、支付、发送、发布、删除必须确认 |
| 审计账本 | P0 | 所有关键事件可追溯 |
| 数据脱敏 | P0 | 发布 session 前必须通过脱敏检查 |
| 访问控制 | P1 | 租户、角色、任务、文件、ledger 权限隔离 |
| 凭证轮换 | P1 | 支持吊销和过期 |
| 结果过期 | P1 | 输出文件支持有效期 |

## 9. 依赖系统可用性

| 外部依赖 | 风险 | 建议 |
|---|---|---|
| Agent Runtime | 模型、CLI、tool schema 变化 | 首发阶段绑定单一 runtime，冻结版本 |
| 第三方生成 API | 超时、限流、额度不足 | 启动前额度探测，失败重试，成本上限 |
| OAuth 服务 | 授权过期、范围不足 | 授权状态检测，重新授权流程 |
| 浏览器自动化 | 页面变化、验证码、登录失效 | 限定场景，State Validator，人工接管 |
| 对象存储 | 文件丢失、下载失败 | 多副本、签名 URL、结果保留策略 |
| 通知通道 | 小程序/短信/企业微信失败 | 多通道降级 |

## 11. 降级与恢复策略

| 故障 | 降级策略 | 恢复策略 |
|---|---|---|
| Agent Runtime 不可用 | 暂停新任务，保留草稿 | 恢复后继续队列 |
| 第三方 API 超时 | 重试、切换备用供应商、等待用户确认 | 记录失败并允许重跑 |
| 文件上传失败 | 本地重试、分片续传 | 恢复上传任务 |
| 通知失败 | 切换短信/企业微信/站内通知 | 用户回到任务页继续 |
| Ledger 写入失败 | 阻断任务终态流转 | 补偿写入后归档 |
| Credential Vault 不可用 | 禁止启动需凭证任务 | 恢复后重新校验授权 |
| State Validator 失败 | 进入人工接管 | Creator 修复 session 版本 |

## 12. 首发阶段可用性边界

### 12.1 首发阶段应支持

| 能力 | 标准 |
|---|---|
| 单任务启动 | 用户可在移动端完成一次任务启动 |
| Slot 表单 | 支持文本、数字、选择、文件、API key |
| 云端运行 | 支持单 runtime、单容器执行 |
| 进度展示 | 支持阶段级进度 |
| 关键确认 | 支持移动端确认动作 |
| 结果交付 | 支持文件和链接结果 |
| 基础 Ledger | 支持运行状态、输入摘要、工具摘要、成本、结果 |
| Creator 发布 | 支持手工导入 session、配置 slot、发布任务 |

### 12.2 首发阶段暂缓

| 能力 | 暂缓原因 |
|---|---|
| 多 runtime 兼容 | session 格式和工具协议差异大 |
| 高风险自动提交 | 合规责任和安全要求高 |
| 公开 marketplace | 质量控制和责任边界复杂 |
| 自动脱敏全流程 | 误判成本高，初期需人工确认 |
| 完整浏览器回放 | 工程量大，基础 trace 可先覆盖 |
| 收益分成 | 依赖供给侧规模 |

## 14. 关键建议

| 优先级 | 建议 | 原因 |
|---|---|---|
| P0 | 首发阶段绑定单一 runtime | 降低 session 兼容复杂度 |
| P0 | 首场景选择短剧生成或素材处理 | 降低外部状态漂移和合规风险 |
| P0 | 建立 run 状态机和 execution ledger | 保证任务可追踪、可恢复、可审计 |
| P0 | Credential Vault 禁止密钥进入 prompt 和 trace 明文 | 降低安全风险 |
| P0 | Cloud Runner 支持队列、超时、心跳、幂等 | 保证运行稳定性 |
| P1 | Slot schema 增加业务校验 | 提高 fork 成功率 |
| P1 | State Validator 覆盖关键节点 | 识别外部系统漂移 |
| P1 | 失败页面面向业务解释 | 提升轻度用户可用性 |
| P1 | Creator 发布前必须测试 fork | 降低发布后失败率 |
| P2 | 增加版本灰度和回滚 | 支持企业生产运行 |

## 15. 最终判断

灵办词元的系统方案具备首发阶段可用性。当前方案在产品入口、用户分层、任务执行链路、权限审计方向上结构完整。

生产级可用性的主要瓶颈集中在以下五项：

1. Session Fork 的状态恢复能力。
2. Cloud Runner 的任务调度和隔离能力。
3. Credential Vault 的安全托管能力。
4. Execution Ledger 的完整审计能力。
5. State Validator 对外部系统漂移的识别能力。

建议第一阶段采用“低风险场景 + 单 runtime + 人工确认脱敏 + 基础 trace + 强审计”的实施策略。达到 首发内测阶段后，再推进浏览器自动化、公开市场、多 runtime 兼容和高风险业务流程。
