## 2. 排期原则表

| 原则 | 含义 |
|---|---|
| 先主链后外围 | 先打通 run 主链，再补治理和资产化 |
| 先权威源后投影层 | 先完成 DB、runtime、API，再推进前端真实联调 |
| 先隔离后规模化 | 先证明 Docker per run 隔离成立，再讨论多租户并发 |
| 先治理高风险能力 | MCP、凭证、文件下载优先纳入治理边界 |
| 强依赖前移 | 被多个仓库依赖的包与接口先交付 |
| 联调提前插入 | 每个大批次结束前必须做一次阶段联调 |

## 3. 排期假设表

| 维度 | 当前假设 |
|---|---|
| 迭代节奏 | 以周为最小节奏单元 |
| 里程碑周期 | 每 2 周形成一次阶段验收 |
| 开发模式 | 多仓并行，但严格遵守关键路径 |
| 首发目标 | H5 + Dashboard + Backend + Runtime 主链可用 |
| 小程序目标 | 首发不作为 gate，保留后续特化 |
| 上线口径 | 不按 MVP 压缩，按完整系统目标推进 |

## 21. 排期风险缓冲表

| 风险 | 最可能影响阶段 | 建议缓冲 |
|---|---|---|
| `packages/db` 选型或 migration 机制反复 | M1 | 为 M1 预留 20%-30% 缓冲 |
| Docker daemon / Windows 本地环境不稳定 | M2 | 将本地联调与 CI runner 验证并行准备 |
| credential 与 MCP 域边界反复 | M3 | 先冻结 DTO / registry / broker 边界再并行实现 |

| Session Pack 领域定义反复 | M5 | 先冻结 manifest 最小集，再推进 import/export |
| auth/org 域过晚启动 | M6 | 在 M4 后半程提前启动 auth 数据模型设计 |
