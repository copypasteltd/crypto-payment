## 3. 当前审批执行链路总表

| 步骤 | 发起方 | 输入 | 执行逻辑 | 输出 | 当前状态 |
|---|---|---|---|---|---|
| 1. 创建实例 | 前端 -> API | `CreateRunInput` | `RunsService.createRun()` 创建 run，同时种入 `createSeedApproval()` | 新 run + 1 条 `pending` 审批 + system prompt | 已实现 |
| 2. 运行启动 | API -> Orchestrator | `StartRunJobPayload` | `runOrchestrator.startRun()` 启动嵌入式运行链 | bridge/worker 开始推动运行 | 已实现 |
| 3. Runtime 请求审批 | bridge/runtime -> API | `approval.requested` 事件 | `ingestBridgeEvents()` 将审批 upsert 到 `approvals` 数组 | 审批对象进入 run 快照 | 已实现 |
| 4. 用户提交审批 | 前端 -> API / WS | `ApproveRunInput` | `RunsService.approve()` 查找首个 `pending` 审批，写入 approved/rejected | 更新 run 状态、更新审批、追加 system message | 已实现 |
| 5. 状态广播 | API -> 前端 | `run.status.changed` + `conversation.message` | 事件总线写入并广播 | Dashboard/Mobile 刷新状态与消息 | 已实现 |
| 6. 命令下发 | API -> bridge | `RunControlCommand(type=approve)` | `bridgeRegistry.dispatch()` 向运行中的 bridge 发命令 | bridge 恢复执行或结束 | 已实现 |
| 7. 前端渲染审批提示 | Dashboard / Mobile | `RunSnapshot.approvals` + `run.status` | Dashboard 用状态标签和建议动作；Mobile 额外生成模块化审批卡 | 用户在对话上下文中继续处理审批 | 已实现 |

## 4. 当前审批状态机与事件映射总表

| 场景 | 触发输入 | `RunApproval.state` | `Run.run.status` | 事件输出 | 当前备注 |
|---|---|---|---|---|---|
| 创建 run | `createRun()` | 新增 `pending` | 初始状态由 `createRunRecord()` 决定，前端多表现为待补充/待输入 | `conversation.message` | 当前存在“已种审批但 run 状态未必进入 `WAITING_APPROVAL`”的口径差异 |
| Runtime 发起新审批 | `approval.requested` | upsert 为 `pending` | 不自动切换，除非另有 `run.status.changed` 事件 | `approval.requested` | 当前审批对象和状态切换未强绑定 |
| 用户批准 | `ApproveRunInput.approved = true` | `pending -> approved` | `RUNNING` | `run.status.changed`、`conversation.message`、bridge `approve` 命令 | 已实现 |
| 用户拒绝 | `ApproveRunInput.approved = false` | `pending -> rejected` | `CANCELLED` | `run.status.changed`、`conversation.message`、bridge `approve` 命令 | 已实现 |
| Runtime 失败 | `run.failed` | 审批状态不变 | `FAILED` | `run.failed` | 失败恢复与审批回流目前未自动联动 |

## 6. Creator 治理模块与运行约束映射总表

| 治理分区 | 当前界面语义 | 目标运行约束 | 当前是否已落到后端/运行时 | 直接缺口 |
|---|---|---|---|---|
| `credentials` | 区分哪些 secret mount，哪些保留为第三方 ref，哪些需要轮换或收紧作用域 | 控制 credential mount mode、注入边界、轮换要求 | 部分落在 `runtime-config` / `secret-manifest` / `mcp-bindings`，无正式治理 API | 缺凭证治理域与轮换链路 |
| `members` | 区分 Creator、治理、审计角色 | 决定谁可发布、谁可审计、谁可查看全部实例 | 未落地 | 缺成员/角色系统 |
| `policy` | 浏览器审批、路径白名单、容器销毁策略 | 决定 target path 边界、容器复用策略、最终提交前审批 | 路径边界在 `file-access.ts` 已有，容器销毁与审批策略未正式编排 | 缺正式策略域 |
| `audit` | 发布前脱敏、调试回放、实例级导出 | 生成 release ledger、replay、audit export | UI 语义存在，后端缺失 | 缺发布审计与回放接口 |
| `cost` | Workspace / account / package 配额与超额回流审批 | 控制 image key、browser runtime、API usage | UI 语义存在，后端缺失 | 缺配额、计费、超额回流链路 |

## 8. 审批与治理的当前关键不一致点

| 不一致项 | 当前表现 | 影响 | 优先级 |
|---|---|---|---|
| 审批对象已创建，但 run 状态不一定进入 `WAITING_APPROVAL` | `createRun()` 会创建 seed approval，但状态流仍可能停在 `CREATED/READY` | 前端和后端对“当前是否处于审批阶段”的语义不完全一致 | P0 |
| `approval.requested` 不自动驱动 run 状态变更 | 需要额外 `run.status.changed` 才能进入 `WAITING_APPROVAL` | 运行时请求审批时容易出现状态与审批数组不同步 | P0 |
| Creator 治理为纯前端语义 | 凭证、成员、策略、审计、成本全未进入正式 API/DB | 治理无法约束真实运行 | P0 |
| 超额、风险、提交前审批尚未形成策略引擎 | 当前只有单一审批动作 | 难以支撑企业复杂流程 | P1 |
| 审批缺失作用域信息 | `RunApproval` 当前没有 risk level、resource scope、required role | 审批粒度太粗 | P1 |
