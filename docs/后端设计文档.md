## 2. 设计目标与边界

本文档定义灵办词元后端的最终目标形态，重点解决以下问题：

| 目标 | 说明 |
|---|---|
| 统一主栈 | 采用 TypeScript 作为后端主语言，覆盖 API、调度、容器桥接、契约定义 |
| Codex 云端运行 | 用户可在网页、小程序、H5 中启动独立 Codex 运行实例 |
| run 级强隔离 | 每个 run 独立 Docker container，容器结束后销毁 |
| session 资产化 | 将可复用 session 以平台自有标准包形式管理 |
| MCP 可扩展 | 同时支持平台托管 MCP、企业托管 MCP、用户自带第三方 MCP |
| 凭证可治理 | 统一管理 API key、OAuth、cookie、MCP 私有凭证 |
| 对话与文件可视化 | 用户可实时与 Codex 对话，并访问 `target path` 文件树 |
| 结果可交付 | 输入输出文件、trace、artifact 可归档、下载、审计 |

本文档明确以下设计边界：

| 边界 | 说明 |
|---|---|
| 主栈固定为 TypeScript | 不采用 Go 作为主控面主栈 |
| 执行隔离固定为 Docker container | 不以宿主进程多租户方式运行 Codex |
| 不依赖 Codex 私有 session 目录作为长期事实源 | 平台维护自己的 canonical session pack |
| MCP 接入分级治理 | 平台不控制第三方 MCP 内部逻辑，只控制连接、凭证、网络、审计边界 |
| 用户只访问 `target path` | 不暴露整个容器文件系统 |

## 3. 总体架构

### 3.1 总体结构

```text
Web / H5 / Mini Program
-> API Server
-> PostgreSQL
-> Redis / BullMQ
-> Run Worker
-> Docker Engine
   -> run container
      -> Container Bridge
      -> Codex CLI
      -> Playwright
      -> optional local MCP helpers
-> S3 / MinIO
-> Vault / KMS
-> external MCP endpoints
```

### 3.2 核心模块

| 模块 | 主技术 | 主要职责 | 是否核心 |
|---|---|---|---:|
| `API Server` | TypeScript + Fastify | 用户、任务、session、run、文件上传、文件下载、实时对话、MCP 注册 | 是 |
| `Run Worker` | TypeScript + BullMQ | 启动/停止容器、生成 run 配置、注入 session、MCP、凭证、回收结果 | 是 |
| `Credential Broker` | TypeScript + Vault/KMS | 统一管理 API key、OAuth、cookie、MCP 私有凭证 | 是 |
| `Container Bridge` | TypeScript | 容器内包装 Codex CLI、管理实时消息、文件树、MCP 配置、本地 helper | 是 |
| `Main Storage` | PostgreSQL + S3/MinIO + Redis | 业务主库、session 包、artifact、缓存和队列 | 是 |

### 3.3 设计原则

| 原则 | 说明 |
|---|---|
| run 是最小执行单元 | 每个 run 独立 container，生命周期独立 |
| session version 是最小可复用资产单元 | 所有继承与复用围绕 session version 进行 |
| 平台保留长期事实源 | 事实源是 PostgreSQL 元数据和 S3 session pack |
| 容器只承载运行期状态 | 容器销毁后不保留私有状态 |
| 用户侧只见任务和文件 | 不暴露 Codex 私有目录和内部实现细节 |
| MCP 接入走统一注册与注入机制 | 不允许前端或 session 直接拼接未受控连接信息 |

## 4. 主技术栈选型

### 4.1 主栈选择

| 域 | 选型 | 具体实现方式 | 选型原因 |
|---|---|---|---|
| 主语言 | `TypeScript 5.x` | API、worker、bridge、shared contracts 全部统一 TS | Codex 对 TS 多模块联动改动效率最高 |
| Node 运行时 | `Node.js 22 LTS` | 所有 TS 服务与 runner image 统一版本 | 稳定，生态完整 |
| HTTP 框架 | `Fastify` | 模块化 route/service/repository 结构 | 显式、轻量、便于长期维护 |
| 参数校验 | `Zod` | 请求入参、出参、slot schema、event schema 统一定义 | 契约与校验同源 |
| API 文档 | `zod-to-openapi` | 自动生成 OpenAPI 文档 | 减少手写接口文档漂移 |
| 队列 | `BullMQ + Redis` | run 异步调度、重试、并发控制 | 简洁，足够支撑容器调度 |
| 数据库 | `PostgreSQL` | 主业务数据、强事务状态 | 适合任务、session、run、审批等控制面数据 |
| 数据访问 | `Drizzle ORM + SQL` | 表结构、迁移、关键查询保留 SQL 控制 | 类型清晰，避免黑盒 ORM |
| 文件存储 | `S3-compatible / MinIO` | session pack、artifact、文件上传下载 | 大对象持久化与签名下载 |
| 凭证托管 | `Vault + KMS` | API key、OAuth token、cookie、临时凭证 | 敏感数据独立边界 |
| 浏览器自动化 | `Playwright + Chromium` | 运行在 runner image 内 | 提供网页控制、录屏、截图、下载能力 |
| Codex 执行控制 | `node-pty` + child process | 以伪终端形式拉起 Codex CLI | 保留 CLI 交互行为并支持实时收发 |

### 4.2 主栈重评

本系统的主栈选择不是“语言偏好问题”，而是“Codex 作为实现主体时，哪种技术栈能更稳定地把整套系统做完整”的问题。

| 候选栈 | 体系化能力 | Codex 构建难度 | 适合度 | 核心判断 |
|---|---:|---:|---:|---|
| `TypeScript` | 9/10 | 低 | 10/10 | 最适合作为统一主栈 |
| `Go` | 9/10 | 高 | 7/10 | 适合基础设施团队，不适合当前主控面首选 |
| `Python` | 6/10 | 中 | 6/10 | 适合专项能力，不适合主控面长期治理 |
| `JavaScript` | 4/10 | 低 | 3/10 | 缺少静态类型约束，不适合作为平台主栈 |

进一步说明如下：

| 评估维度 | TypeScript | Go | Python | 结论 |
|---|---|---|---|---|
| 前后端契约统一 | 强 | 中 | 弱 | TS 最优 |
| Codex 改动联动效率 | 强 | 中 | 中 | TS 最优 |
| Playwright 集成 | 强 | 弱 | 中 | TS 最优 |
| Codex CLI 子进程控制 | 强 | 中 | 中 | TS 最优 |
| session / trace / event JSON 处理 | 强 | 中 | 强 | TS 与 Python强，但 TS 跨层更统一 |
| 长期类型治理 | 强 | 强 | 中 | TS 与 Go 强，但 TS 跨层更一致 |
| shared schema 复用 | 强 | 中 | 弱 | TS 最优 |

最终结论：

| 问题 | 结论 |
|---|---|
| 后端主栈是什么 | `TypeScript` |
| 为什么不是 Go | Go 很适合底层基础设施，但本系统跨前端、浏览器、CLI、schema、MCP 的联动太多，会引入额外 Node 胶水层 |
| 为什么不是 Python | Python 适合 AI 专项模块，不适合控制面和协议层长期治理 |

### 4.3 为什么主栈不是 Go / Python

| 栈 | 不作为主栈的主要原因 |
|---|---|
| `Go` | 控制面强，但浏览器自动化、Codex CLI 进程编排、schema 共享、前后端联动会额外引入 Node 胶水层 |
| `Python` | 原型能力强，但长期控制面边界、类型契约和多服务一致性弱于 TypeScript |
| `JavaScript` | 缺乏静态类型边界，不适合 `session/run/policy` 这类核心对象的长期治理 |

### 5.4 容器启动参数

### 5.5 Worker 启动容器的完整步骤

| 步骤 | 动作 |
|---|---|
| 1 | 从 PostgreSQL 加载 run、session_version、slot_schema、mcp bindings |
| 2 | 从 Vault/KMS 获取本 run 所需凭证 |
| 3 | 从 S3 下载 canonical session pack |
| 4 | 在宿主机创建 run 私有工作目录 |
| 5 | 解包 session pack 到宿主机临时目录 |
| 6 | 生成 run-scoped `runtime-config.json` |
| 7 | 生成 run-scoped `mcp-config.json` |
| 8 | 生成 run-scoped `secrets/*` |
| 9 | 挂载工作目录，启动 Docker container |
| 10 | Bridge 就绪后标记 run 为 `RUNNING` |

### 5.6 runner entrypoint 建议流程

| 顺序 | 动作 |
|---|---|
| 1 | 校验 `/workspace` 目录结构 |
| 2 | 校验 `runtime-config.json`、`mcp-config.json`、secrets 是否存在 |
| 3 | 启动 Container Bridge |
| 4 | Bridge 初始化文件 watcher、artifact uploader、event emitter |
| 5 | Bridge 拉起 Codex CLI |
| 6 | Bridge 建立与 API/Worker 的反向事件通道 |
| 7 | 等待 run 结束、取消或异常退出 |

## 6. 为什么需要 Playwright

Playwright 在本系统中的定位是受控浏览器执行引擎。

| 需求 | Playwright 提供什么 | 对系统的价值 |
|---|---|---|
| 网页自动操作 | locator、自动等待、上传下载、弹窗处理 | 降低网页型任务失败率 |
| 浏览器隔离 | 独立 browser context、独立 profile | 多用户数据不串 |
| 审计和回放 | screenshot、video、trace | 企业场景下可审计可复盘 |
| 与 TypeScript 协同 | 同语言同运行时 | Bridge 和浏览器服务集成成本低 |

说明：

| 约束 | 说明 |
|---|---|
| 浏览器不是全局默认能力 | 仅在任务需要时启用 |
| 浏览器不直接暴露给前端 | 用户通过平台 API 间接控制 |
| 浏览器不共享 profile | 每个 run 独立 browser profile |

### 6.1 浏览器能力的使用边界

| 场景 | 是否启用 Playwright | 理由 |
|---|---:|---|
| API 型任务 | 否 | 不需要浏览器，降低资源消耗 |
| 文件处理型任务 | 否 | 不需要浏览器 |
| 网页填报、后台录入、信息采集 | 是 | 需要真实浏览器行为 |
| 网页登录、文件下载、表单上传 | 是 | 需要 Playwright 能力 |

### 6.2 浏览器状态保存

| 对象 | 保存位置 | 说明 |
|---|---|---|
| browser profile | `/workspace/browser-profile` | 当前 run 私有 |
| screenshot/video | `/workspace/outputs/browser/*` | 归档到 artifact |
| storage state | `/workspace/state/browser-state.json` | 用于 run 内恢复 |

## 7. session 资产模型

### 7.1 session 的分层表达

| 层 | 存什么 | 放在哪里 | 用途 |
|---|---|---|---|
| `Session Metadata` | session id、version、lineage、runtime config、发布状态 | PostgreSQL | 任务与版本管理 |
| `Canonical Session Pack` | 对话、工具事件、workspace base、slot schema、manifest | S3/MinIO | 长期资产、fork 来源 |
| `Run State` | 当前 run 临时状态、容器内增量文件、CLI 私有状态 | 容器本地 `/workspace/state` | 运行时恢复 |

### 7.2 session pack 结构

| 文件 | 用途 |
|---|---|
| `conversation.jsonl` | 原始会话历史 |
| `tool-events.jsonl` | 工具调用历史 |
| `workspace-base.tar.zst` | 基础工作目录快照 |
| `slot-schema.json` | 输入槽位定义 |
| `runtime-config.json` | 运行配置 |
| `manifest.json` | 版本、来源、依赖说明 |
| `validator-set.json` | 关键状态断言 |
| `mcp-requirements.json` | 所需 MCP 类型与凭证要求 |

### 7.3 关键原则

| 原则 | 说明 |
|---|---|
| 不依赖 Codex 私有状态做长期存储 | `codex-home` 只属于 run 时临时缓存 |
| 平台定义自己的资产格式 | session pack 是唯一长期可复用格式 |
| session version 不可变 | 发布后冻结 |

### 7.4 session pack manifest 建议字段

| 字段 | 说明 |
|---|---|
| `session_id` | session 主标识 |
| `session_version` | 当前版本号 |
| `task_family` | 该 session 适用的任务族 |
| `runtime_profile` | 运行环境要求 |
| `slot_schema_version` | 输入槽位版本 |
| `required_capabilities` | 需要的 MCP、浏览器、文件、API 能力 |
| `artifact_contract` | 期望输出物定义 |
| `created_by` | Creator 信息 |
| `created_at` | 版本创建时间 |

### 7.5 session 继承与 fork 规则

| 规则 | 说明 |
|---|---|
| fork 来源固定 | 每个 run 必须绑定具体 `session_version` |
| session pack 只读 | run 期间不回写原 pack |
| run 增量单独保留 | 输出、trace、state 不污染原资产 |
| 如需续跑 | 从 run 的 checkpoint 或 run snapshot 重新生成新 run |

## 8. run 生命周期

### 8.1 run 状态机

| 状态 | 含义 |
|---|---|
| `DRAFT` | 用户填写中 |
| `READY` | 输入和凭证校验完成 |
| `QUEUED` | 已进入队列等待调度 |
| `STARTING` | Worker 正在拉起容器 |
| `RUNNING` | Codex CLI 正在执行 |
| `WAITING_APPROVAL` | 等待用户确认 |
| `SUCCEEDED` | 执行成功 |
| `FAILED` | 执行失败 |
| `CANCELLED` | 用户取消 |
| `ARCHIVED` | 已归档 |

### 8.2 run 执行链路

| 步骤 | 系统动作 |
|---|---|
| 1 | API Server 创建 `run` |
| 2 | 写入 PostgreSQL |
| 3 | 投递 BullMQ 任务 |
| 4 | Run Worker 拉起 Docker container |
| 5 | 下载 session pack 到容器 |
| 6 | 写入用户输入到运行上下文 |
| 7 | Credential Broker 下发 run 所需凭证 |
| 8 | Container Bridge 启动 |
| 9 | Bridge 拉起 Codex CLI |
| 10 | Codex 运行中持续输出消息、文件和事件 |
| 11 | 输出文件上传到 S3/MinIO |
| 12 | 更新 `run` 状态、归档 trace 和 artifact |
| 13 | 销毁容器 |

### 8.3 run 状态迁移规则

| 当前状态 | 可迁移到 | 触发条件 |
|---|---|---|
| `DRAFT` | `READY`、`CANCELLED` | 输入补全或用户取消 |
| `READY` | `QUEUED`、`CANCELLED` | 用户启动或取消 |
| `QUEUED` | `STARTING`、`FAILED` | worker 取到任务或启动失败 |
| `STARTING` | `RUNNING`、`FAILED` | Bridge 就绪或容器初始化失败 |
| `RUNNING` | `WAITING_APPROVAL`、`SUCCEEDED`、`FAILED`、`CANCELLED` | 运行中事件驱动 |
| `WAITING_APPROVAL` | `RUNNING`、`FAILED`、`CANCELLED` | 用户确认、超时、取消 |
| `SUCCEEDED` | `ARCHIVED` | 归档完成 |
| `FAILED` | `ARCHIVED` | 归档完成 |
| `CANCELLED` | `ARCHIVED` | 清理完成 |

### 8.4 超时和回收策略

| 场景 | 策略 |
|---|---|
| 容器启动超时 | 标记 `FAILED`，记录 `container_start_timeout` |
| Codex 无输出超时 | 发送健康探针，仍无响应则终止容器 |
| 等待审批超时 | 标记 `FAILED` 或 `CANCELLED`，按任务配置决定 |
| 文件上传失败 | 重试并标记 artifact 失败状态 |
| 容器退出异常 | Bridge 或 Worker 回收日志并标记 `FAILED` |

## 10. MCP 设计

### 10.1 MCP 分类

| 类型 | 例子 | 连接方式 | 平台控制力 | 风险 |
|---|---|---|---:|---:|
| `platform-managed` | image-gen、browser、seedance helper | 本地进程或本地 helper | 高 | 低 |
| `workspace-managed` | 企业自托管 MCP | 外部 HTTP/SSE/WebSocket | 中 | 中 |
| `user-byo-managed` | 用户自带第三方 MCP | 外部直连 | 低 | 高 |

### 10.2 MCP 接入模式

| 模式 | 场景 | 放在哪里 | Codex 怎么连 |
|---|---|---|---|
| `local-process` | 平台内置 helper | run container 内 | 走 `localhost` 或 stdio |
| `sidecar-service` | 比较重的本地能力 | 同 run 网络环境 | 走内网地址 |
| `remote-managed` | 企业可控 MCP | 外部服务 | 走指定 URL |
| `remote-unmanaged` | 用户第三方 MCP | 外部服务 | 走指定 URL，但受平台策略约束 |

### 10.3 MCP 注册模型

| 字段 | 说明 |
|---|---|
| `mcp_id` | MCP 唯一标识 |
| `type` | platform-managed / workspace-managed / user-byo-managed |
| `protocol` | stdio / http / sse / websocket |
| `endpoint` | 连接地址 |
| `credential_mode` | none / api-key / oauth / cookie / json-file |
| `tool_manifest` | 暴露给 Codex 的工具清单 |
| `risk_level` | trusted / approved / untrusted |
| `workspace_id` | 所属租户 |
| `owner_user_id` | 所属用户 |

### 10.4 MCP 绑定模型

| 字段 | 说明 |
|---|---|
| `binding_id` | 绑定主键 |
| `mcp_id` | 目标 MCP |
| `binding_scope` | user / workspace / session_version / run |
| `credential_id` | 使用的凭证 |
| `enabled` | 是否启用 |
| `approval_required` | 是否首次调用需确认 |
| `network_policy_ref` | 出网白名单引用 |

### 10.5 run 启动时的 MCP 物化

每个 run 启动时，平台生成以下文件：

| 文件 | 作用 |
|---|---|
| `mcp-config.json` | 当前 run 可见的 MCP 服务定义 |
| `mcp-bindings.json` | MCP 与凭证绑定关系 |
| `network-policy.json` | 当前 run 允许访问的外部域名 |
| `secrets/*.json` | 运行期临时凭证 |

示意配置：

```json
{
  "servers": {
    "imageGenInternal": {
      "type": "local-process",
      "command": "node",
      "args": ["/workspace/mcp/imagegen-helper.js"]
    },
    "workspaceNotionMcp": {
      "type": "remote-managed",
      "url": "https://mcp.example.com/sse",
      "auth_env": "MCP_NOTION_TOKEN"
    },
    "userRemoteMcpA": {
      "type": "remote-unmanaged",
      "url": "https://third-party-mcp.example.org/mcp",
      "auth_file": "/workspace/secrets/user-remote-mcp-a.json"
    }
  }
}
```

### 10.6 第三方不受控 MCP 的处理原则

| 原则 | 说明 |
|---|---|
| 平台不控制第三方 MCP 内部逻辑 | 只控制连接边界和风险边界 |
| 平台生成 run-scoped 配置 | 每个 run 独立 MCP 配置，不共享 |
| 平台控制凭证注入 | 不允许用户直接把明文密钥写进 session |
| 平台控制出网范围 | 仅允许访问该 run 已批准的 MCP 域名 |
| 平台记录边界调用 | 至少记录调用了哪个 MCP、何时调用、结果状态 |

### 10.7 各类 MCP 的推荐接入方式

| MCP 类型 | 推荐接入方式 | 原因 |
|---|---|---|
| 平台托管 image-gen | `local-process` | 控制力最强，便于审计 |
| 平台托管 browser helper | `local-process` 或 `sidecar-service` | 本地能力最稳定 |
| 企业自托管 MCP | `remote-managed` | 可由管理员治理 |
| 用户第三方 MCP | `remote-unmanaged` | 必须保留 BYO-MCP 能力，但纳入强提示和白名单机制 |

## 11. 凭证设计

### 11.1 凭证类型

| 凭证类型 | 归属 | 示例 | 生命周期 |
|---|---|---|---|
| 用户私有凭证 | user | image-gen API key、Google OAuth | 用户管理 |
| 工作区共享凭证 | workspace | 企业统一 Seedance key | 管理员管理 |
| session 所需凭证 | session_version | 某任务必须要的第三方 key | 版本要求 |
| run 临时凭证 | run | 本次运行下发的短时 token 或临时 JSON | run 生命周期 |

### 11.2 注入方式

| 场景 | 注入方式 | 说明 |
|---|---|---|
| 简单 API key | 环境变量或临时 `.env` 文件 | 适合 image gen、REST API |
| JSON 凭证 | 临时 JSON 文件 | 适合第三方 MCP 复杂配置 |
| OAuth access token | 临时环境变量或临时文件 | 只下发 access token，不下发 refresh token |
| cookie/session state | 临时文件 | 适合浏览器类能力 |

### 11.3 凭证注入原则

| 原则 | 说明 |
|---|---|
| 最小注入 | 只下发当前 run 需要的凭证 |
| 临时有效 | 容器销毁后凭证失效 |
| 不进 trace | trace 只记录引用，不记录明文 |
| 不把 refresh token 给 Codex | 凭证续签由平台完成 |
| 不共享凭证目录 | 每个 run 独立 `/workspace/secrets` |

### 11.4 凭证生命周期

| 阶段 | 系统动作 |
|---|---|
| 创建 | 用户或管理员在平台录入凭证，保存到 Vault/KMS |
| 绑定 | 凭证绑定到 user/workspace/session/MCP |
| 启动 run | Credential Broker 为该 run 生成最小凭证集合 |
| 物化 | 在宿主机临时目录生成文件或 env 清单 |
| 注入 | 随容器挂载进入 `/workspace/secrets` |
| 使用 | Bridge 和 Codex 通过引用路径访问 |
| 销毁 | 容器删除后凭证文件消失 |
| 轮换 | 原凭证轮换后，新 run 使用新版本凭证 |

### 11.5 凭证文件布局建议

```text
/workspace/secrets
  /api
    image-gen.env
    seedance.env
  /oauth
    google-drive.json
  /mcp
    user-remote-mcp-a.json
  /browser
    login-cookie.json
```

### 11.6 凭证与 session 的关系

| 规则 | 说明 |
|---|---|
| session version 只声明“需要什么凭证类型” | 不直接保存凭证明文 |
| run 才绑定具体 credential instance | 避免资产层和密钥耦合 |
| 同一 session 在不同用户 run 中可绑定不同凭证 | 满足多租户使用 |

## 15. 隔离与安全

### 15.1 隔离策略

| 隔离维度 | 方案 |
|---|---|
| 进程隔离 | 每个 run 一个独立 Docker container |
| 文件隔离 | 每个 run 独立 `/workspace` 目录 |
| HOME 隔离 | `HOME=/workspace/home` |
| Codex 状态隔离 | `CODEX_HOME=/workspace/codex-home` |
| 浏览器隔离 | Playwright profile 放在 `/workspace/browser-profile` |
| 凭证隔离 | `/workspace/secrets` run 私有 |
| MCP 配置隔离 | 每个 run 独立 `mcp-config.json` |
| 网络隔离 | 每个 run 按白名单访问所需域名 |
| 文件可见性隔离 | 用户仅可见 `target path` |

### 15.2 宿主机与容器的边界

| 层 | 可见内容 | 不可见内容 |
|---|---|---|
| 前端用户 | run 状态、消息、target path、下载文件 | 宿主机、Vault、Docker socket |
| API Server | run 元数据、artifact 元数据、部分实时事件 | 容器内明文凭证 |
| Run Worker | 宿主机工作目录、容器管理接口 | 用户原始前端会话 |
| Container Bridge | 容器内文件、Codex 输出、本 run 凭证文件 | 其他 run 的状态 |
| Codex CLI | 当前 run 的 workspace、mcp config、secrets 引用 | 平台数据库、其他 run 数据 |

### 15.3 第三方 MCP 风险治理

| 信任级别 | 适用对象 | 平台策略 |
|---|---|---|
| `trusted` | 平台托管 MCP | 默认允许，完整审计 |
| `approved` | 企业审核通过的第三方 MCP | 白名单域名、工具白名单 |
| `untrusted` | 用户自带外部 MCP | 默认关闭或强提示，仅显式授权后启用 |

### 15.4 第三方 MCP 的核心事实

| 事实 | 说明 |
|---|---|
| 平台不能控制第三方 MCP 内部行为 | 只能控制连接、凭证、网络、审计边界 |
| 一旦启用第三方 MCP，数据可能被发送到外部服务 | 必须做明确授权和风险提示 |
| 平台必须记录 MCP 调用边界日志 | 至少知道哪个 run 在何时调用了哪个 MCP |

### 15.5 不允许暴露的容器路径

| 路径 | 原因 |
|---|---|
| `/workspace/secrets` | 含明文或临时敏感凭证 |
| `/workspace/state` | 含内部状态、恢复文件 |
| `/workspace/home` | 含运行时历史配置 |
| `/workspace/codex-home` | 含 Codex 私有状态 |
| `/workspace/tmp` | 可能含临时敏感文件 |

## 16. 部署结构

### 16.1 基础部署

| 组件 | 建议部署方式 |
|---|---|
| API Server | 常驻 Node 服务 |
| Run Worker | 常驻 Node worker |
| Docker Engine | 与 worker 同主机或独立执行节点 |
| PostgreSQL | 托管数据库或独立实例 |
| Redis | 独立实例 |
| MinIO/S3 | 独立对象存储 |
| Vault/KMS | 独立密钥服务 |

### 16.2 单机/单区域部署建议

| 节点 | 建议角色 |
|---|---|
| `api-node` | API Server + Redis + MinIO 前置接入 |
| `worker-node` | Run Worker + Docker Engine |
| `db-node` | PostgreSQL + Vault/KMS |

说明：

| 策略 | 说明 |
|---|---|
| API 与 Worker 可先分机部署 | 避免容器执行影响 API 稳定性 |
| Docker Engine 不暴露公网 | 仅 Worker 可控制 |
| 对象存储统一走内部网络 | 降低 artifact 传输成本 |

### 16.2.1 当前 Local Dev 拓扑基线

| 组件 | 当前落地方式 |
|---|---|
| PostgreSQL / Redis / MinIO | `infra/docker/docker-compose.local.yml` |
| API | `infra/docker/api.Dockerfile` + `infra/docker/api-entrypoint.sh`，容器启动前自动执行 migration |
| Host Worker | `infra/scripts/run-local-worker.mjs` 读取 `infra/docker/worker.host.env` 后以前台 daemon 方式启动 |
| Local Bootstrap | `infra/scripts/local-stack.mjs`，通过 `pnpm infra:local:up` / `pnpm infra:local:dev` 收口 |
| Runner Image | `infra/docker/runner.Dockerfile` 构建 `lingban/runner:local` |

当前基线的作用是把 Local Dev 从“手动多命令拼接”推进到“标准脚本启动 + 自动迁移 + worker 探针可观测”的可重复联调形态。

### 16.3 为什么当前不引入更重基础设施

| 组件 | 当前不引入的原因 |
|---|---|
| Kafka | 当前核心问题是 run 隔离和 Codex 容器化执行，不是高吞吐事件总线 |
| Temporal | 当前设计已用容器 + Worker + 队列表达完整链路，不必先引入更重工作流引擎 |
| Kubernetes | 当前要求明确以 Docker container 作为 run 隔离单元，后续再上 K8s 不影响抽象边界 |

### 16.4 后续演进兼容性

| 当前设计 | 后续可平滑演进到 |
|---|---|
| BullMQ | Temporal 或更强工作流系统 |
| Docker Engine 单机调度 | Kubernetes Job / Pod |
| 单机 Worker | 多执行节点调度器 |
| 本地 MinIO | 托管 S3 |
| 单区域部署 | 多区域或专属私有化部署 |

## 17. 关键实现建议

| 优先级 | 建议 | 原因 |
|---|---|---|
| P0 | 先实现 `Container Bridge` | 它是 Codex 对话、文件、MCP 的统一桥梁 |
| P0 | 先固化 runner image | 运行环境必须先冻结 |
| P0 | 先定义 session pack 规范 | 平台长期资产格式必须先统一 |
| P0 | 先定义 MCP 注册与注入规范 | 第三方能力接入不能后补 |
| P0 | 先约束 `target path` | 用户文件访问边界必须先定 |
| P1 | 增加 run checkpoint | 为长任务和断线恢复做准备 |
| P1 | 增加审批事件 | 支持高风险动作确认 |
| P1 | 增加 Bridge 到 API 的结构化事件协议 | 便于 Web/H5/小程序统一消费 |

### 17.1 开工顺序建议

| 阶段 | 必须交付 |
|---|---|
| Phase 1 | runner image、Bridge、run 容器启动链路 |
| Phase 2 | session pack、文件上传下载、target path 浏览 |
| Phase 3 | MCP registry、credential broker、第三方 MCP 接入 |
| Phase 4 | 审批、artifact 归档、trace 包 |
| Phase 5 | 运维、回收、监控、轮换、恢复机制 |

## 18. 最终结论

灵办词元后端采用 TypeScript 作为主栈，围绕 `API Server + Run Worker + Credential Broker + Container Bridge + Main Storage` 五个核心部分构建。

系统的关键设计点如下：

| 主题 | 结论 |
|---|---|
| 主栈 | TypeScript |
| 执行隔离 | 每个 run 一个 Docker container |
| Codex 运行 | runner image 内固定版本 Codex CLI，由 Bridge 以 App Server stdio 主协议拉起；PTY 仅保留受控回滚 |
| 浏览器执行 | Playwright 内置于 runner image |
| session 持久化 | 平台自有 canonical Session Pack v2，保留原始事件、Workspace、签名和 Replay 证据 |
| MCP 接入 | 支持平台托管、企业托管、用户自带第三方 MCP |
| 凭证治理 | 统一走 Credential Broker 和 Vault/KMS |
| 用户交互 | WebSocket 实时对话 |
| 文件访问 | 只暴露 `target path`，支持实时浏览和下载 |
| 长期事实源 | PostgreSQL 元数据 + S3 session pack / artifacts |

## 19. Session Control 设计落地补充（2026-07-17）

| 设计项 | 已落地决策 |
